# Аутентификация

DCM поддерживает локальные учётные данные и вход через Keycloak/OIDC.

## Локальная аутентификация

Параметры начального администратора и доступные в браузере способы входа задаются в `backend/.env`:

```env
SSO_ADMIN_USERNAME=admin
SSO_ADMIN_EMAIL=admin@example.com
SSO_ADMIN_PASSWORD=<надёжный-случайный-пароль>
SSO_LOCAL_LOGIN_ENABLED=true
SSO_LOCAL_REGISTER_ENABLED=true
```

- `SSO_LOCAL_LOGIN_ENABLED` управляет входом по имени пользователя и паролю.
- `SSO_LOCAL_REGISTER_ENABLED` управляет самостоятельной регистрацией.
- Bootstrap admin остаётся резервной локальной учётной записью. Войти им можно только по паролю, поэтому восстановление доступа через него требует `SSO_LOCAL_LOGIN_ENABLED=true`: отдельного способа входа для bootstrap admin нет.
- SSO не запускается, если выключены и `SSO_LOCAL_LOGIN_ENABLED`, и `SSO_OIDC_ENABLED`: войти было бы некому. Если выключен только локальный вход, а `SSO_OIDC_ADMIN_GROUPS` пуст, SSO при старте пишет предупреждение: администратор может не суметь войти.
- Минимальная длина локального пароля на границе HTTP API — 6 символов; для администратора используйте более длинный случайный пароль.

## Модель токенов DCM

1. Вход по паролю или обратный вызов OIDC создаёт отдельную сессию в PostgreSQL SSO и случайный одноразовый refresh-токен в HttpOnly cookie. В базе хранится только его SHA-256 хеш.
2. Клиентская часть получает короткоживущий токен доступа через `/api/v1/auth/refresh`.
3. Access-токен остаётся JWT с идентификатором сессии; Gateway проверяет его через SSO, включая актуальное состояние пользователя и сессии.
4. Выход отзывает текущую сессию на сервере и затем удаляет cookie. Другие устройства сохраняют свои сессии.

При обновлении старый refresh-токен атомарно заменяется новым. Повторное использование старого токена отзывает всю его сессию, включая access JWT. Дублирующий запрос или потерянный ответ могут потребовать нового входа; браузер координирует обновления между вкладками через Web Locks. Без поддержки Web Locks одновременные вкладки могут вызвать повторный вход.

Сессия действует не более 30 дней после входа и истекает через 7 дней без обновления. Access JWT действует до 15 минут, но отзыв сессии блокирует последующие проверки сразу после фиксации отзыва. Смена пароля или деактивация отзывает все сессии пользователя; повторная активация их не восстанавливает. Активные потоки и уже разрешённые запросы сохраняют свои существующие сроки.

`/auth/refresh` и `/auth/logout` требуют `Origin` из `CORS_ALLOWED_ORIGINS` либо допустимый `Referer`, если `Origin` отсутствует. При `401` обновления cookie удаляется. При `503`, `504` или сетевой ошибке cookie сохраняется, действия приостанавливаются и предлагается повторить запрос либо войти заново. Ответы с токенами имеют `Cache-Control: no-store`.

Выход DCM не завершает сессию Keycloak: следующий явный OIDC-вход может пройти без повторного ввода пароля провайдера. После перехода на сессии требуется новый вход; старые refresh JWT и access JWT без идентификатора сессии не поддерживаются. Полный контракт описан в документе [о безопасности сессий](session-security.md).

Для развёртывания по HTTP используются:

```env
COOKIE_SECURE=false
COOKIE_HTTP_ONLY=true
COOKIE_SAMESITE=lax
```

При появлении HTTPS необходимо изменить origins/URLs и установить `COOKIE_SECURE=true`.

## OIDC через Keycloak

В текущей версии Keycloak является единственным поставщиком OIDC, к которому DCM подключается напрямую. Других поставщиков удостоверений можно подключить через Keycloak в качестве посредника.

Основные переменные:

```env
SSO_OIDC_ENABLED=true
SSO_OIDC_ISSUER_URL=http://keycloak.localhost/realms/dcm
SSO_OIDC_CLIENT_ID=dcm
SSO_OIDC_CLIENT_SECRET=<секрет-клиента>
SSO_OIDC_REDIRECT_URL=http://localhost/api/v1/auth/oidc/keycloak/callback
SSO_OIDC_ADMIN_GROUPS=/dcm-admins,dcm-admin
SSO_OIDC_DEFAULT_ROLE=user
```

Выключенный OIDC (`SSO_OIDC_ENABLED=false`, значение по умолчанию) не создаёт поставщика: SSO не обращается к Keycloak и не запускает фоновых задач, список поставщиков в `/api/v1/auth/providers` пуст, а маршруты `/api/v1/auth/oidc/keycloak/start` и `/callback` отвечают `404`.

При `SSO_OIDC_ENABLED=true` обязательны `SSO_OIDC_ISSUER_URL`, `SSO_OIDC_CLIENT_ID`, `SSO_OIDC_CLIENT_SECRET` и `SSO_OIDC_REDIRECT_URL`; issuer и redirect URL должны быть абсолютными адресами `http` или `https`. Если значение отсутствует или неверно, SSO не запускается и называет переменную, не выводя её значение.

### Недоступный Keycloak

Недоступность Keycloak не мешает запуску SSO. SSO обращается к метаданным Keycloak в фоне: сразу после старта, затем с паузой от 1 секунды, удваивая её до 60 секунд, пока попытка не удастся. Каждая неудача пишется в журнал как предупреждение, успешное подключение — один раз. Перезапуск не нужен.

Пока SSO не связался с Keycloak, поставщик считается включённым, но недоступным:

- вход по паролю, обновление сессии и проверка токенов доступа работают как обычно;
- `/api/v1/auth/providers` отдаёт поставщика с `"available": false`;
- маршруты start и callback отвечают `503`;
- на странице входа кнопка Keycloak неактивна и показывает подсказку, а страница настроек показывает отдельно, что поставщик включён и что связи с ним нет.

### Настройка Keycloak для разработки

1. Запустите дополнительный Compose-файл:

   ```bash
   docker compose --env-file backend/.env \
     -f docker-compose.yml \
     -f backend/docker-compose.keycloak.yml \
     up -d keycloak_db keycloak
   ```

2. Откройте `http://keycloak.localhost`.
3. Создайте realm `dcm`.
4. Создайте confidential OpenID Connect client `dcm`.
5. Включите client authentication и standard authorization code flow.
6. Добавьте valid redirect URI `http://localhost/api/v1/auth/oidc/keycloak/callback`.
7. Добавьте post logout redirect `http://localhost/*` и web origins `http://localhost`, `http://localhost:5173`.
8. Скопируйте client secret в `SSO_OIDC_CLIENT_SECRET` и перезапустите SSO/Gateway.


### Сопоставление ролей

DCM сопоставляет группы и роли области Keycloak со значениями из `SSO_OIDC_ADMIN_GROUPS`. Чтобы назначать роль администратора:

- создайте группу `/dcm-admins` или роль области `dcm-admin`;
- добавьте преобразователь, включающий `groups` и/или `realm_access.roles` в ID-токен;
- назначьте группу или роль нужным пользователям.

Пользователь OIDC создаётся при первом успешном входе. Внешний идентификатор пользователя остаётся постоянным; имя пользователя и адрес электронной почты могут синхронизироваться при последующих входах. При конфликте с локальным именем пользователя или адресом электронной почты автоматическое создание учётной записи отклоняется.

## Безопасность потока OIDC

Gateway устанавливает привязанный к браузеру файл cookie `oidc_state` с атрибутом HttpOnly. SSO проверяет состояние, одноразовое значение, издателя и код авторизации при обратном вызове. После него Gateway устанавливает файл cookie с токеном обновления DCM и перенаправляет одностраничное приложение на `/auth/callback`; токены DCM не появляются в строке запроса.

## Диагностика

- Если provider не отображается, проверьте `SSO_OIDC_ENABLED` и `/api/v1/auth/providers`.
- Если provider отображается с `"available": false`, SSO ещё не получил метаданные Keycloak: проверьте предупреждения `oidc provider discovery failed` в журнале SSO и доступность `SSO_OIDC_ISSUER_URL` из контейнера SSO.
- Если callback отклонён, сравните issuer, redirect URI и browser origin без отличий в scheme/host/port.
- Если admin role не назначается, проверьте token mappers и точное значение group/role.
- После изменения OIDC env перезапустите `sso` и `gateway`.
