# Модель безопасности

Документ описывает, как DCM разграничивает доступ между пользователями, службами и сетями на одном сервере. Он нужен владельцу сервера, который оценивает риски, и разработчику, который меняет границы доверия. Переменные окружения перечислены в [справочнике конфигурации](configuration.md).

## Границы доверия

| Граница | Что защищает |
| --- | --- |
| Gateway — единственная HTTP-точка входа | Каждый запрос проверяется через SSO; роль в клиентской части не является авторизацией |
| Учётные данные служб и политики вызовов | Ни одна внутренняя служба, кроме Gateway, не может действовать от имени пользователя или администратора |
| Отдельная bridge-сеть каждого пользователя | Контейнеры разных владельцев не видят друг друга |
| Изоляция `proxy_net` | Опубликованные контейнеры достижимы только из Traefik, а не друг из друга |
| Внутренняя сеть сборок с egress-прокси | Dockerfile получает внешний HTTP(S), но не внутренние службы и частные адреса |
| Токены реестра на одну сборку | Сборка читает и пишет только образы своего владельца |

Core и Builder имеют доступ к Docker socket. Компрометация любой из этих служб равна компрометации сервера, какими бы ни были политики вызовов: политики ограничивают то, что служба может попросить у Core и SSO, но не то, что она может сделать с хостом.

## Учётные данные служб

Каждая вызывающая служба знает только свои учётные данные (`GATEWAY_SERVICE_TOKEN`, `CORE_SERVICE_TOKEN`, `BUILDER_SERVICE_TOKEN`), а сервер — учётные данные тех служб, которые он принимает. Сервер определяет вызывающую службу по учётным данным и применяет её политику:

| Сервер | Вызывающая служба | Разрешённые вызовы | Область действия (scope) |
| --- | --- | --- | --- |
| Core | Gateway | Все RPC, кроме четырёх вызовов Builder; все внутренние HTTP-маршруты | `user`, `admin`, `system` |
| Core | Builder | Только `StartBuildRecord`, `CompleteBuildRecord`, `GetBuildStatus`, `GetBuilderRuntimeConfig`; HTTP-маршрутов нет | только `system` |
| SSO | Gateway | Все RPC | `user`, `admin`, `system` |
| SSO | Core | Только `GetUser` и `BatchGetUsers` | только `system` |

- Только Gateway может заявить область `user` или `admin`. Обработчик никогда не действует от имени человека, а скомпрометированный Builder, который распаковывает недоверенные архивы, не может перечислить, остановить или удалить ресурсы пользователей через Core или SSO.
- Неизвестные учётные данные и запрос без области отклоняются как неаутентифицированные (`Unauthenticated`, HTTP `401`); вызов или область вне политики — как запрещённые (`PermissionDenied`, HTTP `403`). Проверки области внутри обработчиков и служб остаются второй линией защиты.
- Служба не запускается, если её учётные данные не заданы, пусты или совпадают с учётными данными другой службы; сообщение называет переменную, но не её значение.
- Итоговые журналы запросов Core и SSO содержат ключ `caller` с именем вызывающей службы; сами учётные данные в журналы не попадают.

Внутренний gRPC и HTTP работают без TLS в частных сетях Docker одного сервера. Взаимный TLS тоже аутентифицировал бы службы, но на одном сервере добавил бы выпуск и ротацию сертификатов, не защищая ничего сверх отдельных учётных данных в частных сетях. Решение нужно пересмотреть, если Builder будет работать на другой машине: тогда его учётные данные пойдут через сеть, которую DCM не контролирует.

## Пользователи и сессии

- Токены доступа DCM — короткоживущие JWT, привязанные к сессии в PostgreSQL SSO; Gateway проверяет каждый токен через SSO, включая состояние пользователя и сессии. Токен обновления — одноразовый случайный секрет в HttpOnly cookie; в базе хранится только его SHA-256. Токены не передаются в URL.
- Деактивация пользователя и смена пароля отзывают все его сессии; деактивация также останавливает его контейнеры и отменяет сборки и развёртывания.
- Keycloak используется только как внешний поставщик входа по authorization code с PKCE; токены DCM ему не передаются.

Полный контракт сессий: [безопасность сессий](session-security.md). Настройка входа: [аутентификация](authentication.md).

## Пользовательские контейнеры

- Контейнеры не запускаются в привилегированном режиме, с `network_mode: host` или `pid: host`; подключения каталогов сервера запрещены. Те же запреты действуют для Compose (см. [руководство по Compose](compose-guide.md#запрещённые-возможности)).
- Порты сервера не пробрасываются: публикация идёт только через Traefik и `proxy_net`.
- Пользовательские контейнеры и контейнеры сборки создаются с `oom_score_adj` 500, поэтому при нехватке памяти OOM killer выбирает их раньше служб платформы. Жёсткую границу памяти даёт родительская cgroup `TENANT_CGROUP_PARENT` (см. [развёртывание](deployment-single-vm.md#ограничение-памяти-пользовательских-контейнеров)).
- Терминал запускает только команды из списка `telemetry_allowed_exec_commands`. Журналы и терминал открываются по короткоживущему одноразовому билету, а не по JWT в URL.

### Изоляция опубликованных контейнеров

Опубликованные контейнеры всех пользователей подключены к общей сети `proxy_net`. Служба `build-network-policy` устанавливает цепочку `DCM-PROXY`: трафик внутри bridge `PROXY_BRIDGE_NAME` разрешён, только если его источник или получатель — Traefik (`TRAEFIK_PROXY_IP`); остальной трафик внутри bridge отбрасывается (в IPv6 — весь). Трафик из `proxy_net` в другие сети не меняется. Core запускается только после готовности политики, а healthcheck политики требует, чтобы bridge `PROXY_BRIDGE_NAME` существовал.

### Граница Gateway

Gateway доверяет `X-Forwarded-For` только от Traefik на отдельной внутренней сети `dcm_gateway_ingress`; Traefik не доверяет forwarded-заголовкам внешних клиентов. Лимиты частоты аутентификации и загрузок и аудит используют один и тот же проверенный адрес клиента. Не подключайте пользовательские контейнеры к сети `dcm_gateway_ingress`. Настройка — в [справочнике конфигурации](configuration.md#gateway-и-файлы-cookie).

## Реестр образов

Реестр — upstream Distribution (`registry:2.8.3`, закреплён по digest) с собственной token-аутентификацией на всех адресах.

- Порт `127.0.0.1:5000` принадлежит TCP-пересылке `registry-edge`, которая передаёт TLS только в отдельный аутентифицированный listener Core. Этот listener обслуживает только `/token` и `/v2/`; plaintext HTTP и служебные пути Core на нём недоступны.
- Сам Registry не публикует порты и находится в отдельной внутренней сети `registry_net`. Не добавляйте его в `build_net`, `dcm_net` или в сеть Traefik. API реестра проверяет подпись и права даже при прямом обращении.
- Core подписывает токены реестра отдельной RSA-парой (`signing.key` подключается только в Core); издатель `dcm-core` одинаков у Core и Registry. Компрометация ключа подписи требует замены доверия реестра.

### Учётные данные сборки

После того как сборка надёжно захвачена, Core выдаёт для неё единственный случайный учётный данный для обмена на токены, сохраняя только его SHA-256. Он действует до сохранённого срока выполнения сборки. Kaniko получает его в `/kaniko/.docker/config.json`, вне контекста сборки и снимка образа, но **считайте, что Dockerfile может его прочитать**. В очереди, аргументах сборки и пользовательских DTO его нет; он удаляется вместе с контейнером сборки. Kaniko v1.24.0 закреплён по digest, проверка TLS включена.

| Кто | Права |
| --- | --- |
| Сборка | `pull,push` только для своего репозитория назначения и `pull` для других образов своего владельца. Удаление, каталог и чужие репозитории запрещены; права действуют на все теги репозитория |
| Docker daemon при загрузке образа | Отдельный продлеваемый учётный данный на чтение одного репозитория сроком 30 минут; в контейнер приложения не попадает |
| Очистка и метаданные в Core | Отдельный принципал Core с `pull,delete` для одного репозитория, подписываемый внутри Core |

Bearer-токен действует 60 секунд; Distribution допускает ещё 60 секунд расхождения часов, поэтому серверу нужны синхронизированные часы. Отмена сборки сразу запрещает продление и ставит сохраняемую очистку, которая ждёт 181 секунду после последней выдачи токена, — дольше любого выданного токена. Удаление образа выполняется после такой же паузы и только когда сборки соседних тегов того же репозитория завершились: bearer даёт права на все теги. Новая сборка репозитория не запускается, пока идёт удаление в нём.

## Сеть сборок

Контейнеры сборки работают во внутренней сети `build_net` (`172.30.252.0/24`) без прямого доступа в интернет. В ней доступны только:

- `registry-edge` (`172.30.252.2:5000`) — пересылка TLS в listener реестра Core; сам Core к сети сборки не подключён;
- egress-прокси `build-egress` (`172.30.252.3:3128`) — разрешает внешние HTTP/HTTPS-адреса и запрещает частные и link-local. Dockerfile получает его через `HTTP_PROXY`/`HTTPS_PROXY`; клиенты, игнорирующие прокси, прямого доступа в интернет не получают.

`build-network-policy` (нужны `CAP_NET_ADMIN` и host network) устанавливает правила IPv4/IPv6 в forwarding Docker и в INPUT хоста. Требуются iptables backend Docker, цепочка `DOCKER-USER`, `br_netfilter` и обе настройки `bridge-nf-call`, равные `1`. Правила сохраняются при остановке контейнера политики. Builder проверяет внутренний bridge и здоровье политики перед захватом сборки и перед запуском Kaniko; healthcheck проверяет сами правила, а не только файл готовности. Если политика ещё не восстановилась после перезапуска Docker, сборка остаётся в очереди и Kaniko не запускается.

Не отключайте политику, не подключайте контейнеры сборки к другим сетям и не используйте имена bridges `br-dcm-build`, `br-dcm-egress`, `br-dcm-proxy` для других сетей. Проверка правил на сервере: [проверка сетевой политики хоста](deployment-single-vm.md#проверка-сетевой-политики-хоста).

Аргументы сборки — не канал для секретов: они могут попасть в слои образа. Не передавайте через них пароли и токены.

## Аудит и отчёты

- Gateway проверяет разрешение `reports.admin.read` для всех пяти операций отчётов, включая ручное обновление снимков. Core повторно требует область `admin` с идентификатором инициатора; области `user` и `system` доступа к отчётам и чтению аудита не дают.
- События аудита записывает Core от имени вызывающего: поля инициатора (`actor_user_id`, `actor_username`, `actor_scope`) Core всегда берёт из области запроса и заменяет одноимённые поля события. Пользователь и администратор записывают события только от своего имени; системное событие имеет область `system` без пользователя. Через внутренний API аудита события может записывать только Gateway (Builder этот API вызвать не может); собственные события Core записывает сам.
- Аудит — best effort: ошибка хранилища аудита не отменяет основную операцию.
- Журналы и сведения аудита не содержат учётных данных, токенов, значений переменных окружения, аргументов сборки, ввода и вывода терминала, ключей объектов и необработанных ошибок вышестоящих служб.

Какие события записываются, описано в [руководстве администратора](admin-guide.md#отчёты-и-аудит).

## Что не защищено

- Трафик между браузером и сервером идёт по HTTP: HTTPS штатно не поддерживается.
- Высокой доступности и резервирования нет; резервное копирование настраивает владелец сервера (см. [эксплуатацию](operations.md#резервное-копирование)).
- Docker Engine, ядро и образы ОС служб обновляет владелец сервера. Образы Alpine и реестра не сканируются на CVE пакетов ОС (см. [руководство разработчика](development.md#toolchain-и-входные-данные-сборки)).
