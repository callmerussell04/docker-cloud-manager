# Руководство разработчика

Документ описывает локальную разработку DCM: инструменты, генерацию кода, тесты, CI, закреплённые версии и проверку уязвимостей. Установка платформы на сервер описана в [инструкции по развёртыванию](deployment-single-vm.md).

## Рабочие каталоги

- Команды `docker compose` для всего стека выполняются из корня репозитория.
- Go- и Make-команды backend — из `backend/`.
- npm-команды — из `frontend/`.

## Требования

| Инструмент | Для чего |
| --- | --- |
| Go | Make сам выбирает Go **1.26.11** через `GOTOOLCHAIN`; первый запуск может скачать toolchain |
| `protoc` 34.1 | Генерация protobuf; [protobuf v34.1](https://github.com/protocolbuffers/protobuf/releases/tag/v34.1) в `PATH` или `make PROTOC=/path/to/protoc ...` |
| Docker Engine и плагин Compose | `make test`, Docker smoke-тесты и весь стек |
| `jq` | `make vulncheck` |
| Node.js 24 | Клиентская часть (тот же образ `node:24-alpine` собирает её в Docker) |

Остальные инструменты (golangci-lint v2.11.4, mockery v2.53.6, protoc-gen-go v1.36.11, protoc-gen-go-grpc v1.6.2, gotestsum v1.13.0, govulncheck v1.9.0) Make устанавливает фиксированных версий в игнорируемый `backend/bin/tools/`. Глобальная установка не нужна, но первый запуск требует доступа к Go module proxy.

Для прямых Go-команд задавайте `GOTOOLCHAIN=go1.26.11`: директива `go` в `go.mod` — только минимум и не мешает выбрать более новый установленный компилятор.

## Команды backend

| Команда | Назначение |
| --- | --- |
| `make verify` | Все проверки без интеграционных сервисов по порядку, до первой ошибки: `check-format` (gofmt), `check-generated`, `check-tidy` (`go mod tidy -diff`), `build`, `vet`, `lint`, `test-race` |
| `make build` | Сборка четырёх бинарников; не форматирует и не меняет зависимости |
| `make tidy` | Форматирование и `go mod tidy` |
| `make test-fast` | Быстрые тесты без интеграционных сервисов |
| `make test-race` | Быстрые тесты с race detector |
| `make test` | Полный набор с временной инфраструктурой (см. ниже) |
| `make vet`, `make lint` | `go vet`; golangci-lint, включая архитектурные правила `depguard` |
| `make vulncheck` | Проверка уязвимостей (см. [ниже](#проверка-уязвимостей)) |
| `make fuzz` | Фаззинг парсера Compose, распаковщика архивов, URL Git-репозитория и тега образа, каждый по `FUZZ_TIME` (по умолчанию `30s`) |
| `make run` | Запуск всего стека для разработки |
| `make dev-certs` | Одноразовые сертификаты реестра для личной машины (нужен `sudo`) |

Сборка использует read-only module metadata, отключает CGO и удаляет локальные пути и VCS metadata (`-mod=readonly -trimpath -buildvcs=false`).

`make fuzz` запускается только локально; CI проигрывает сохранённые входные данные в обычном прогоне тестов. Найденный падающий вход Make записывает в `testdata/fuzz/<Target>/` пакета — добавьте его в коммит вместе с исправлением.

## Генерация кода

```bash
make generate-mocks  # mockery; игнорируемый internal/testutil/mocks/
make generate-proto  # protoc-gen-go и protoc-gen-go-grpc
make generate        # оба генератора
make check-generated # подготовка моков и проверка protobuf без перезаписи файлов
```

Моки не хранятся в git: `backend/.mockery.yml` явно перечисляет интерфейсы, поэтому новый интерфейс добавьте туда до использования его мока. Сгенерированный protobuf хранится в git: после изменения `.proto` выполните `make generate-proto` и включите результат в коммит. `make test-fast` и `make test` сами готовят моки и отклоняют расхождение protobuf; перед прямым `go test` выполните `make generate-mocks`.

## Тесты

Модульные тесты лежат рядом с кодом, межмодульные — в `backend/tests/integration/`.

### Полный набор

```bash
cd backend
make test
```

Команда поднимает PostgreSQL, ClickHouse, RabbitMQ и MinIO на loopback-портах из `backend/docker-compose.test.yml`, включает Docker smoke-тесты и двухвладельческую проверку изоляции реестра и удаляет тестовые контейнеры, сети и тома после успеха или ошибки, включая сбой запуска. Пакеты выполняются параллельно с race detector. Ожидание запуска ограничено 120 секундами, тесты пакета — пятью минутами, RPC общей Core-фикстуры — пятью секундами.

`make test` задаёт `DCM_TEST_REQUIRE_INTEGRATION=1`, поэтому интеграционный тест без нужного окружения падает, а не пропускается. Исключения — две ручные проверки сервера, которые меняют хост или требуют особой файловой системы: [сетевая политика хоста](deployment-single-vm.md#проверка-сетевой-политики-хоста) и [ограничение размеров томов ядром](deployment-single-vm.md#ограничение-размеров-томов).

| Переменная | Назначение |
| --- | --- |
| `TEST_KEEP_ENV=1` | Сохранить окружение для диагностики; затем выполните `make test-env-down` |
| `TEST_PKGS` | Выбрать пакеты |
| `TEST_ARGS`, `TEST_ALL_ARGS` | Переопределить флаги Go-тестов |
| `TEST_COMPOSE_PROJECT` | Изолировать имена ресурсов Compose; порты хоста всё равно должны быть свободны |
| `DCM_CLICKHOUSE_TEST_DB`, `DCM_CLICKHOUSE_TEST_USER`, `DCM_CLICKHOUSE_TEST_PASSWORD` | Параметры и сервера, и тестового клиента (по умолчанию `dcm_reports_test`, `dcm_reports_test`, `clickhouse`) |

### Изоляция реестра отдельно

Двухвладельческая проверка изоляции реестра входит в `make test`. Ей нужны Docker и доступ к закреплённым образам Registry и Kaniko. Отдельный запуск (только с одноразовой тестовой базой данных):

```bash
cd backend
GOTOOLCHAIN=go1.26.11 CORE_TEST_REGISTRY_ISOLATION=1 CORE_TEST_DATABASE_URL='postgres://.../dcm_core_test?sslmode=disable' \
  go test -count=1 -timeout=5m ./tests/integration/registry_isolation
```

Тест создаёт собственные хранилище Registry, bridge и контейнеры выполнения, проверяет настоящие `RUN` в Dockerfile с прочитанным учётным данным сборки и удаляет свои fixtures. Firewall хоста он не устанавливает.

## CI

GitHub Actions workflow `Backend` (`.github/workflows/backend.yml`) запускает `make verify`, `make test` и `make vulncheck` отдельными jobs при push и pull request с изменениями в `backend/` или `deployment/`; еженедельное расписание повторяет только `make vulncheck`. У workflow только права чтения репозитория, actions закреплены по commit, protoc 34.1 — по checksum, у jobs есть таймауты. При сбое интеграционных тестов выводятся состояние и журналы тестовых сервисов, после чего они удаляются.

Ни один job CI не собирает Docker-образы служб и реестра.

## Обязательные зависимости служб Core

Конструкторы служб Core проверяют полноту зависимостей при запуске: отсутствующая зависимость, включая typed nil, приводит к ошибке запуска до старта обработчиков. Проверки допуска, блокировки ёмкости и резервы ресурсов никогда не отключаются из-за неполного адаптера: неполный адаптер просто не реализует нужный интерфейс.

| Служба | Обязательно | Необязательно |
| --- | --- | --- |
| Контейнеры (`service.NewContainerService`) | Репозиторий с блокировкой владельца и ёмкости, проверкой очереди, атомарной записью контейнера, операции и outbox; репозитории томов и образов с учётом диска; Docker с проверкой томов; метрики RAM, CPU и диска; runtime config; пользователи SSO; счётчик активных сборок | Аудит; удаление скачанного образа при ошибке (best effort) |
| Допуск сборок | Репозитории сборок, образов, томов, контейнеров и staged objects; пользователи; runtime config; метрики RAM, CPU и диска | Объектное хранилище подключается лениво; его недоступность не мешает запуску |
| Проекты | Репозитории проектов и ресурсов проекта; Docker; жизненный цикл контейнеров и томов; проверка ёмкости; runtime config | Очистка пользовательской сети; отмена Compose-развёртывания |
| Координатор Compose | Состояние развёртываний; сборки и клиент сборок; контейнеры и список контейнеров проекта; тома; Docker; очистка образов; освобождение staged-исходника; runtime config | Аудит публикации сервисов |

Создание и запуск контейнера удерживают блокировку допуска до сохранения резерва, желаемого состояния, операции и outbox; отдельного пути сохранения контейнера без жизненного цикла нет. Цикл зависимостей между проектами и контейнерами разрешает `SetProjectStatusUpdater`, который Core вызывает после создания обеих служб и до запуска обработчиков.

## Toolchain и входные данные сборки

DCM закрепляет Go **1.26.11** — поддерживаемый патч-релиз ветки 1.26. При обновлении сверяйтесь с [политикой выпусков Go](https://go.dev/doc/devel/release) и [официальными загрузками](https://go.dev/dl/?mode=json). Версия 1.26.11 исправляет:

- [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) — denylist скомпрометированных промежуточных сертификатов в `crypto/x509`. Сканирование достигает `Certificate.Verify` через TLS-рукопожатия, и каждый бинарник использует этот верификатор в своих HTTPS/TLS-клиентах, поэтому уязвимость закрыта обновлением, а не принята.
- [GO-2026-6859](https://pkg.go.dev/vuln/GO-2026-6859) — падение HTTP/1-сервера `net/http` из-за гонки заголовков в `MaxBytesReader`; достижима из каждого бинарника.

`backend/go.mod` задаёт минимум 1.26.11, а канонические Make-цели экспортируют ровно `GOTOOLCHAIN=go1.26.11`. При обновлении синхронизируйте версию модуля и закрепления во всех четырёх Dockerfile. Загрузка toolchain проверяется checksum database Go; не отключайте эту проверку.

Все четыре Dockerfile служб используют проверенные multi-platform image indexes:

| Вход | Закреплённая ссылка |
| --- | --- |
| Компилятор | `golang:1.26.11-alpine3.24@sha256:ae52b5bc6ed045a9ed26ab03dc19327a802a9cc9aa8b27ed57f5c6b60579b0bb` |
| Среда выполнения | `alpine:3.24@sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6` |

Docker-сборка задаёт `GOTOOLCHAIN=local`, поэтому изменение модуля не может незаметно скачать другой компилятор. Загрузки модулей сверяются с `go.sum` из git и проверяются `go mod verify`. Локальная и Docker-сборка используют `CGO_ENABLED=0` и `-mod=readonly -trimpath -buildvcs=false`. Core и Gateway дополнительно устанавливают `ca-certificates` и `git`; APK проверяет подписи пакетов. Базовые образы закреплены по digest, а версии APK-пакетов — нет: пересборка ставит текущие пакеты закреплённой ветки Alpine, получает исправления ОС, и образы не воспроизводятся побайтно.

Образы реестра в `deployment/registry/` используют тот же runtime index и такие же незакреплённые APK-пакеты: `socat` (edge), `squid` (egress) и `iptables` (сетевая политика). После обновления базового образа проверьте `squid.conf` командой `squid -k parse`. Compose и тест изоляции реестра запускают upstream-образ Distribution `registry:2.8.3@sha256:a3d8aaa63ed8681a604f1dea0aa03f100d5895b6a58ace528858a7b332415373`.

Остальные сторонние образы в `docker-compose.yml`, `backend/docker-compose.test.yml` и `backend/docker-compose.keycloak.yml` закреплены точными тегами без digest: `postgres:17.10-alpine3.23`, `migrate/migrate:v4.19.1`, `clickhouse/clickhouse-server:25.5.11.15`, `rabbitmq:4.3.1-management`, `traefik:v3.6.20`, `quay.io/keycloak/keycloak:26.8.2` и `pgsty/minio:RELEASE.2026-08-04T00-00-00Z`. Точный тег исключает незаметное обновление minor/major-версии, но издатель может пересобрать его, поэтому такие загрузки не воспроизводятся побайтно. Обновляйте теги намеренно и одинаково во всех Compose-файлах.

Объектное хранилище использует `pgsty/minio` — поддерживаемый сообществом форк MinIO, потому что upstream-образ `minio/minio` больше не загружается из Docker Hub и Quay. Форк сохраняет entrypoint, команду `minio`, переменные `MINIO_ROOT_*`, том `/data` и встроенный `curl` для healthcheck, поэтому служба Compose не меняется. Клиент хранилища DCM использует только базовые операции S3 с объектами и бакетами и работает с другими S3-совместимыми серверами, но службы Compose привязаны к MinIO: другому серверу понадобятся своя команда, переменные учётных данных и healthcheck в обоих Compose-файлах.

Автоматической проверки этих закреплений нет, и CI не собирает образы, поэтому следите за ними при ревью. `make vulncheck` проверяет только Go-бинарники: образы Alpine и upstream-образ реестра не сканируются на CVE пакетов ОС.

## Проверка уязвимостей

`make vulncheck` устанавливает govulncheck v1.9.0 в версионированный игнорируемый каталог инструментов, проверяет `./cmd/...` (production roots без тестовых) и отдельно `bin/builder`, `bin/core`, `bin/gateway` и `bin/sso`. Все проверки выполняются, даже если одна нашла уязвимости, затем применяется политика `backend/vulncheck/policy.json`. Каждая принятая запись называет проверки, к которым относится, дату ревью, обоснование и ссылки на доказательства.

Цель завершается ошибкой:

- при находке уровня символа, не принятой для этой проверки;
- при принятой записи, которую проверка больше не находит;
- при неполной записи.

Находки только уровня модуля или пакета govulncheck выводит, но они не проваливают проверку — так же, как собственные коды завершения govulncheck. Добавляйте запись только после ревью уязвимости относительно вызовов DCM; если есть исправленная версия, предпочитайте обновление.

База уязвимостей живая: цель печатает время её изменения, а CI повторяет проверку еженедельно. Сравнивая результаты, записывайте дату, компилятор, версию сканера, GOOS/GOARCH и параметры сборки. Ручные эквиваленты — `CGO_ENABLED=0 govulncheck ./cmd/...` и `govulncheck -mode=binary bin/<service>` после `make build`; компилятор и параметры показывает `go version -m`. Наличие символа в бинарнике — консервативное доказательство, а не доказательство того, что недоверенный запрос достигает уязвимой операции. Уязвимости сторонних модулей требуют отдельной оценки зависимостей и транспорта.

### Применимость к стандартной библиотеке

- [GO-2026-4869](https://pkg.go.dev/vuln/GO-2026-4869): недоверенные tar-архивы достигают `archive/tar.Reader.Next` в Builder через его распаковщик и адаптер хранилища. Исправлено в Go 1.25.9 / 1.26.2 и входит в закреплённый toolchain. Это значимая граница парсера, но не доказанная эксплуатация DCM.
- [GO-2026-6608](https://pkg.go.dev/vuln/GO-2026-6608): Core принимает multipart-загрузки сборок и Compose через `Request.MultipartReader` и `Reader.NextPart`, которые разбирают MIME-заголовки. Уязвимость — выделение памяти под произвольно длинную строку, когда остаток лимита памяти парсера меньше 400 байт; исправлено в Go 1.26.9 / 1.27.2. Одних лимитов загрузки недостаточно, чтобы считать её неприменимой. Закреплённый toolchain содержит исправление.
- Закреплённый toolchain также содержит исправления TLS, X.509, HTTP, URL, MIME и textproto из примечаний к выпускам Go. Платформенные и неиспользуемые протокольные находки оцениваются относительно Linux-сборок служб и реальных вызовов, без общих исключений.

### Сетевые зависимости

| Модуль | Версия | Причина |
| --- | --- | --- |
| `google.golang.org/grpc` | 1.83.2 | Защита от буферизации и флуда кадров HTTP/2, отклонение запросов без authority |
| `golang.org/x/net` | 0.60.0 | Исправления trailer, window, flow-control и HPACK в HTTP/2; ранее — IDNA |
| `github.com/rabbitmq/amqp091-go` | 1.15.0 | Границы кадров и полей, обработка учётных данных SASL, исправления переподключения |
| `github.com/quic-go/quic-go` | 0.59.1 | Бэкпорт проверки trailer в HTTP/3 |

Требования gRPC и x/net определяют также версии x/crypto, x/sys, x/text, x/sync и genproto RPC; OpenTelemetry поднят отдельно (см. [поднятые косвенные модули](#поднятые-косвенные-модули)). Protobuf — 1.36.11, как у закреплённого генератора. При обновлении просматривайте [выпуски gRPC](https://github.com/grpc/grpc-go/releases), выпуски AMQP [1.13](https://github.com/rabbitmq/amqp091-go/releases/tag/v1.13.0), [1.14](https://github.com/rabbitmq/amqp091-go/releases/tag/v1.14.0), [1.15](https://github.com/rabbitmq/amqp091-go/releases/tag/v1.15.0) и [QUIC 0.59.1](https://github.com/quic-go/quic-go/releases/tag/v0.59.1).

- **gRPC.** DCM использует собственный HTTP/2-транспорт gRPC. Внутренняя аутентификация не закрывает разбор кадров до аутентификации. Закреплённая версия исправляет [GO-2026-6061](https://pkg.go.dev/vuln/GO-2026-6061), [GO-2026-6348](https://pkg.go.dev/vuln/GO-2026-6348) и [GO-2026-6443](https://pkg.go.dev/vuln/GO-2026-6443). DCM не настраивает xDS и его RBAC; эти части отчётов не относятся к авторизации DCM по типизированной области доступа и токенам. Строгие пути RPC включены. Проверка authority в TLS использует leaf-сертификат: настраивайте имена служб по нему. Неожиданные ошибки gRPC проходят через безопасное отображение ошибок DCM.
- **x/net.** Стандартная библиотека и x/net исправляются отдельно. Закреплённая x/net исправляет GO-2026-4918, GO-2026-5026, GO-2026-6603, GO-2026-6610, GO-2026-6611, GO-2026-6612 и GO-2026-6617. Оценивайте HTTP/2 сервера и клиента отдельно; развёртывание по HTTP/1 не исключает gRPC.
- **AMQP.** Исправления разбора касаются вредоносного или скомпрометированного брокера, а не прямого неаутентифицированного HTTP-запроса. DCM использует сохраняемые JSON-публикации, подтверждения, durable quorum queues с DLX, ручные ACK/NACK и `prefetch=1`. AMQPS из URI требует минимум TLS 1.2; Compose для разработки использует AMQP. Автоматическое восстановление соединений выключено (`Config.Recovery` равен nil): переподключение и топологию ведёт DCM. Core использует один publisher для всех outbox. Каждая публикация ограничена 10 секундами на получение соединения, установку TCP/TLS/AMQP, объявление топологии, запись и подтверждение; более ранний срок вызывающего имеет приоритет. Неудачная попытка отбрасывает соединение и поток подтверждений, поэтому запоздавший ACK не подтвердит следующее сообщение. Запись outbox помечается опубликованной только по ACK брокера; сообщение, чей ACK потерян, может быть доставлено повторно.
- **QUIC.** Gin импортирует поддержку HTTP/3, но DCM не запускает QUIC listener и не использует HTTP/3-клиент. Закреплённый бэкпорт quic-go всё равно исправляет GO-2026-5676.
- **Gorilla WebSocket** закреплён на pseudo-version `v1.5.4-0.20240701034025-d67f41855da4` — коммите исправления сразу после v1.5.3, потому что ни один тег не исправляет [GO-2026-6278](https://pkg.go.dev/vuln/GO-2026-6278) (ключи маски из math/rand, вернувшиеся в v1.5.3). Core только принимает серверные соединения, которые не генерируют ключи маски, но символы попадают в бинарник, и проверка на них падает. Перейдите на тег, как только он будет содержать исправление.

### Поднятые косвенные модули

`backend/go.mod` требует эти косвенные модули выше версий, которые выбирают зависимости, потому что те версии содержат достижимые уязвимости:

| Модуль | Версия | Исправляет | Достигается через |
| --- | --- | --- | --- |
| `github.com/andybalholm/brotli` | 1.2.7 | [GO-2026-6888](https://pkg.go.dev/vuln/GO-2026-6888), избыточное выделение памяти на специальных потоках | `clickhouse-go` (отчёты) |
| `github.com/klauspost/compress` | 1.20.2 | [GO-2026-6865](https://pkg.go.dev/vuln/GO-2026-6865), panic на кадрах из двух блоков | `minio-go` (объектное хранилище) |
| `go.opentelemetry.io/otel`, `/trace`, `/metric` | 1.47.0 | [GO-2026-6974](https://pkg.go.dev/vuln/GO-2026-6974), обход ограничения длины атрибутов | клиент Docker SDK (Builder, Core) |

Несколько модулей требуют их более низких версий (`clickhouse-go`, `ch-go`, `minio-go`, `moby/go-archive` и `golang-migrate` — compress; `clickhouse-go` и `golang-migrate` — brotli; gRPC, `clickhouse-go`, `ch-go` и `golang-migrate` — OpenTelemetry), поэтому `go mod tidy` сохраняет эти требования только потому, что они наибольшие. OpenTelemetry 1.47 в свою очередь поднимает `testify` до 1.12.1. Не понижайте их при изменении зависимостей: `make vulncheck` упадёт, если версия опустится ниже исправления.

### Принятые и остаточные уязвимости

`backend/vulncheck/policy.json` сейчас не принимает ни одной уязвимости: ни одна проверка не находит уязвимостей уровня символа, и любая новая находка проваливает `make vulncheck`. Находки уровня модуля всё равно требуют оценки применимости.

Остаточная применимость сознательно уже, чем общее исключение модуля:

- GO-2026-4883 касается проверки привилегий при установке плагинов Docker daemon, GO-2026-4887 — плагинов AuthZ daemon и слишком больших тел запросов. Они были приняты, пока база относила их ко всему модулю; теперь записи называют только пакеты daemon `plugin` и `pkg/authorization`, которые DCM не импортирует, поэтому проверки их не находят и принятие снято. DCM использует клиент и типы Docker и не открывает установку плагинов. Это исключает серверные операции из бинарников DCM, но не освобождает от оценки сам Docker daemon на сервере. Исправленного выпуска Docker SDK нет; обновляйте Engine отдельно. См. upstream-описания [привилегий плагинов](https://github.com/moby/moby/security/advisories/GHSA-pxq6-2prw-chj9) и [AuthZ](https://github.com/moby/moby/security/advisories/GHSA-x744-4wpc-v9h2).
- GO-2026-6253 касается распаковки архивов и исправлена в `moby/go-archive` 0.3.3. Builder напрямую вызывает только `go-archive.TarWithOptions`, чтобы создать несжатый tar рабочего каталога; загрузки распаковывает отдельный распаковщик DCM, а не `go-archive.Untar`. См. [описание уязвимости](https://github.com/moby/go-archive/security/advisories/GHSA-hfg8-hc9c-6c3h). GO-2026-5841 (compress/s2 `NewDict`) исправлена в `klauspost/compress` 1.18.7.
- Находки уровня модуля не игнорируются молча. Уязвимости копирования архивов Docker daemon GO-2026-5617/5668/5746 касаются кода Engine, которого нет в production-графе DCM. Но Builder передаёт tar-потоки через API копирования архивов daemon, поэтому Engine на сервере должен быть версии 29.5.1 или новее (см. [требования](deployment-single-vm.md#1-требования)): отсутствие кода в графе вызовов DCM не исправляет старый Engine. GO-2026-5932 касается x/crypto/openpgp, который production-граф DCM не импортирует; локальные пароли хешируются bcrypt.

Эти исключения действуют только для Linux/amd64-сборок служб; другие платформы и новые вызовы протоколов, копирования или аутентификации требуют повторной оценки.
