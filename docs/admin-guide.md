# Руководство администратора

Роль `admin` предоставляет доступ к управлению пользователями, ресурсами, настройками во время работы, мониторингом, отчётами и журналом аудита.

## Первый вход

Bootstrap admin создаётся SSO при старте из `SSO_ADMIN_USERNAME`, `SSO_ADMIN_EMAIL` и `SSO_ADMIN_PASSWORD`. Храните эти credentials как recovery-доступ даже при включённом OIDC.

## Пользователи

Администратор может создавать и просматривать пользователей, менять профиль, роль, статус, пароль и квоты.

| Поле | Назначение |
| --- | --- |
| `role` | `user` или `admin` |
| `status` | `active` или `deactivated` |
| Квота процессора | Максимальная доля процессора, которую может зарезервировать пользователь |
| Квота памяти | Максимальный объём зарезервированной оперативной памяти |
| Дисковая квота | Ограничение учитываемых дисковых ресурсов |

Удаление пользователя означает деактивацию, а не физическое удаление. Его прежние ресурсы и сведения о владельце сохраняются. Деактивированный пользователь не может войти, обновить токен или выполнять защищённые запросы.

Система не позволяет деактивировать или понизить последнего активного администратора.

## Ресурсы всех пользователей

Раздел **All resources** («Все ресурсы») позволяет просматривать контейнеры, тома, образы, сборки и проекты всех владельцев и выполнять разрешённые действия над ними. Объекты передачи данных административного API могут содержать служебные поля, которых нет в пользовательском API.

Перед удалением ресурса проверьте его владельца, состояние и зависимости. При удалении проекта тома сохраняются. Используемый том или образ нельзя удалить, пока от него зависят другие ресурсы.

## Мониторинг и допуск операций

Раздел мониторинга показывает ресурсы сервера и актуальные показатели допуска операций:

- `admission_status` — доступность новых операций;
- `admission_reasons` — причины ограничения;
- `host_min_free_disk_bytes` — минимальный остаток места;
- `dcm_reserved_build_memory_bytes` — память, зарезервированная занятыми слотами сборки (не больше `max_concurrent_builds`);
- фактические и зарезервированные ресурсы процессора и оперативной памяти;
- состояние Docker и управляемых ресурсов.

Механизм допуска одновременно учитывает пользовательские квоты, резервы в базе данных, слоты сборки, объём подготовленных данных, свободные ресурсы процессора и памяти сервера, а также прогноз свободного места на диске. Не увеличивайте пользовательскую квоту, если причиной отказа является нехватка ресурсов самого сервера.

### Резервы, лимиты и нехватка памяти

- Резерв памяти и CPU контейнера учитывается при допуске и в квоте пользователя. По умолчанию `overcommit_factor` равен `1`, поэтому сумма резервов не превышает память, оставленную пользователям.
- Жёсткий лимит памяти и потолок CPU равны резерву, умноженному на `max_burst_multiplier` и `max_cpu_burst_multiplier`. Они задаются при создании и запуске контейнера и не меняются во время его работы: запуск чужого контейнера не уменьшает лимиты уже работающих.
- Контейнеры вместе могут занять больше памяти, чем зарезервировали. Когда свободной памяти в пуле пользовательских контейнеров становится меньше `memory_pressure_min_free_bytes`, платформа останавливает контейнеры, превысившие свой резерв, начиная с наибольшего превышения. Остановленный контейнер получает состояние `exited` и причину в `last_error`; владелец может запустить его снова. В журнале Core каждая такая остановка записывается с фактической памятью и резервом контейнера.
- Предупреждение `user memory pool is short but no container exceeds its reservation` означает, что памяти не хватает, хотя все контейнеры укладываются в резервы: увеличьте `reserved_system_memory_bytes`, если память занимают службы платформы, или уменьшите `overcommit_factor`.
- Проверка выполняется раз в `memory_pressure_interval_seconds` и не успевает за резким ростом потребления. Жёсткую границу даёт родительская cgroup `TENANT_CGROUP_PARENT` с ограничением памяти: см. [развёртывание](deployment-single-vm.md#ограничение-памяти-пользовательских-контейнеров). Без неё последней защитой остаётся OOM killer сервера.
- Сборки резервируют ресурсы сервера только по числу одновременно выполняемых (`max_concurrent_builds`). Очередь сборок не блокирует запуск контейнеров.

## Отчёты и аудит

Отчёты используют ClickHouse и не являются основным источником сведений о ресурсах.

- Обзор показывает сводные показатели и время последнего снимка `last_usage_snapshot_at`.
- Использование ресурсов пользователем содержит историю процессора, оперативной памяти, диска и количества ресурсов.
- Обновление запускает внеочередное создание снимка и возвращает ответ до его фактического завершения.
- Журнал аудита содержит инициатора, действие, результат, ресурс и безопасные дополнительные сведения.

Если ClickHouse недоступен, операции с ресурсами продолжают работать, но отчёты могут вернуть код `503`. Не считайте отсутствие свежего снимка признаком нулевого потребления.

Gateway проверяет разрешение `reports.admin.read` для всех пяти операций отчётов, включая ручное обновление снимков. Core повторно проверяет типизированную область доступа: нужен `admin` с ненулевым идентификатором инициатора. Области `user`, `system` и отсутствие административной области не дают доступа к сводке, спискам использования, временным рядам, чтению аудита или обновлению, даже при верном внутреннем токене. Периодический сбор снимков выполняется отдельным внутренним методом и не требует административного запроса.

Записывать аудит через внутренний `ReportAPI` могут только вызывающие с верным внутренним токеном и допустимой областью `user`, `admin` или `system`. Общий внутренний токен обозначает доверенный сервис; отдельных удостоверений сервисов этот API не различает. По общему внутреннему транспортному контракту отсутствие метаданных области означает `system`, но не предоставляет административных прав. Прямые вызовы сервиса Core без типизированной области отклоняются.

Core всегда берёт `actor_user_id`, `actor_username` и `actor_scope` из области вызывающего, заменяя одноимённые поля события. Пользователь и администратор записывают события только от своего имени; системное событие имеет область `system` без пользовательского идентификатора и имени. Идентификатор владельца ресурса остаётся отдельным полем и не заменяет инициатора. Gateway сохраняет область и идентификатор запроса при записи аудита после отмены HTTP-запроса; ошибка хранилища аудита не отменяет основную операцию.

## Настройки, изменяемые во время работы

Страница **System settings** («Системные настройки») изменяет рабочие настройки Core. Новый набор значений проверяется целиком и применяется к последующим операциям или циклам фоновых обработчиков.

Основные группы:

- резервирование ресурсов контейнеров, переподписка ресурсов, кратковременное превышение лимитов, время жизни, ограничения процессов и журналирование;
- ограничения количества контейнеров и томов;
- сборки, Kaniko и ограничения загружаемых файлов;
- обработчики Compose, время ожидания и ограничения очереди;
- источники Git и список разрешённых серверов;
- интервал формирования отчётов;
- резерв свободного места на диске;
- ограничения журналов и терминала, а также список разрешённых команд.

Уже запущенные сборки и сеансы терминала обычно не перенастраиваются. Начальные секреты, строки подключения к базам данных, адреса служб, порты, пути хранения и учётные данные поставщика OIDC не входят в рабочие настройки.

Полный перечень приведён в [справочнике конфигурации](configuration.md#настройки-изменяемые-во-время-работы).
